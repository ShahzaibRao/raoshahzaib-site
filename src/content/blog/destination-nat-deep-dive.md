## Destination NAT (DNAT)

### What is DNAT ?

In the previous chapter ([9. From Container to Internet: A Deep Dive into Source NAT](/blog/source-nat-deep-dive/) ), we discussed how, when a network packet travels from a container through the host to the external network, **`Source NAT`** usually modifies the packet’s source address (`src`).

Now, when the network packet returns from the external network back to the host, how does the system know which container it should be delivered to?

**`Destination NAT (DNAT)`** refers to modifying the **`destination IP`**** or ****`port`** of a packet when it enters the internal network (inbound traffic), allowing external requests to be directed to an internal host or service.

In other words, its purpose is:

> “To route external requests to a specific internal service.”

This mechanism is also known as **`Port Forwarding`** or **`Reverse-proxy-style NAT`**.

### Where does Destination NAT take effect?

![Diagram: Where does Destination NAT take effect?](/images/destination-nat-deep-dive/01-destination-nat-deep-dive.png)
From the diagram on the left, we can see that Destination NAT is located in the **`PREROUTING`** and **`OUTPUT`** chains.

A closer inspection of the **`Netfilter hooks`** in **Linux Kernel 6.16** also confirms this.

**The Hooks of `DNAT` in Linux Kernel**

```c

		.revision	= 0,
```

> Question:

> Why does DNAT need to register hooks in **both** the `PREROUTING` and `OUTPUT` chains?

**Answer**

#### **Different Packet Sources**

The reason lies in the **different origins of packets**, which determine the **netfilter chains** they pass through:

| Packet Source | Traversed Hooks | Hook Requiring DNAT |
| --- | --- | --- |
| Incoming from external network | PREROUTING → (LOCAL\_IN / FORWARD) | PREROUTING |
| Generated by local process | OUTPUT → POSTROUTING | OUTPUT |


1. **PREROUTING for 『Forwarding-Type』 DNAT**
This is the most common scenario:

   ```bash
   $ iptables -t nat -A PREROUTING -d 203.0.113.5 -p tcp --dport 8080 -j DNAT --to-destination 10.0.0.5:80
   ```

📦 The traffic originates **from an external source** — the packet enters the network interface and then goes into `NF_INET_PRE_ROUTING`.

At this stage, DNAT intervenes in the `PREROUTING` chain to modify the **destination IP** to `10.0.0.5`.

After that, the kernel’s **routing subsystem** uses the new destination IP to route the packet to the correct internal host.

✅ Applicable scenario: ***The packet comes from an external source, and the system needs to forward it to an internal host.***
2. **OUTPUT for 『Locally Generated』 DNAT**
> The packet is generated by a local process, and you want to change its destination before it leaves the host.

In this case, the packet does **not** pass through `PREROUTING` (since it’s not “coming from outside”),

so DNAT must be attached to the `NF_INET_LOCAL_OUT` hook instead.

   ```bash
   $ iptables -t nat -A OUTPUT -d 127.0.0.1 -p tcp --dport 8080 -j DNAT --to-destination 127.0.0.1:80
   ```

With this rule, when you run `curl http://127.0.0.1:8080`, the request is actually redirected to `127.0.0.1:80`.

✅ Applicable scenario: **Packets generated by local applications also need to be redirected (loopback or internal redirection).**

### Step 4. Observing DNAT in Action

![Diagram: Step 4. Observing DNAT in Action](/images/destination-nat-deep-dive/07-destination-nat-deep-dive.png)
From the lower part of the left figure, we can observe that a packet from **machine-2 (box-2)** passes through **machine-1 (box-1)**’s `eth0` interface with the following details:

- `src`: 172.16.0.3:59610
- `dst`: 172.16.0.2:12345

However, after the packet traverses **machine-1 (box-1)**’s `docker0` interface, its destination is modified by **DNAT** as follows:

- `src`: 172.16.0.3:59610
- `dst`: ***172.17.0.2:80***

This demonstrates that the `docker0` bridge performs **DNAT translation** for us.


### Step 5. Check the rules in the `nat` table of `iptables`

![Diagram: Step 5. Check the rules in the nat table of iptables](/images/destination-nat-deep-dive/08-destination-nat-deep-dive.png)

**`Rule 1`**** **

- `A PREROUTING`
The rule is added to the **PREROUTING chain of the NAT table**. PREROUTING is processed **before the routing decision**, i.e., before the kernel decides whether to deliver the packet locally or forward it.
- `m addrtype`
Uses the **addrtype** match module (the kernel determines the address type, not just a string comparison).
- `-dst-type LOCAL`
Matches packets whose **destination is considered 『LOCAL』** by the system, meaning the target IP belongs to one of the host’s interfaces (e.g., public IP, private IP, bridge IP, docker0 IP).
- `j DOCKER`
If the above conditions are met, jump to the **DOCKER chain**, where Docker places DNAT rules to redirect packets to the container.
**`Rule 2`**

- Packet is **not from ****`docker0`** (i.e., comes from external network or the host itself)
- Protocol is **TCP** and destination port is **12345**
- Packet is **DNAT’ed** to `172.17.0.2:80`

In short, all packets hitting **host TCP port 12345** are redirected to the container IP `172.17.0.2` on port 80. (This usually results from running Docker with `-p 12345:80`)


#### Actual Packet Flow

1. An external client connects to the host’s (machine 1) public IP on port 12345 → the packet arrives at `eth0`.
2. The kernel processes NAT rules in **PREROUTING**: `dst-type LOCAL` check confirms that the destination IP is **local **(because of** ****`docker0`**** **bridge), so the match succeeds.
3. The packet jumps to the **DOCKER** chain, which contains `p tcp --dport 12345 -j DNAT --to-destination 172.17.0.2:80`. The packet is thus **DNAT’ed** to destination `172.17.0.2:80`.
4. Routing is recalculated, and the packet is forwarded to `docker0` → enters **FORWARD** → delivered to the container.

(If the request originates from the host itself, **PREROUTING** does not apply. Instead, the **OUTPUT** rule `-A OUTPUT ! -d 127.0.0.0/8 -m addrtype --dst-type LOCAL -j DOCKER` handles it. Together, these rules support both external and local connections to the host IP.)

## **Conclusion**

In this chapter, we explored the principles of **Destination NAT** and, through experimentation, observed that when a packet arrives at the host from an external network via the `eth0` interface, the `docker0` bridge performs **DNAT**, allowing the packet to reach the actual container.

Combined with what we previously learned about **Source NAT**, we now have a clear understanding of the complete journey of packets entering and leaving a container.
